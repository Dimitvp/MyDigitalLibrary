## What we built

ASP.NET Core Identity with cookie authentication (plan section 8): a real
`ICurrentUser` reading `HttpContext.User`, a global EF Core query filter on every
`IUserOwned` entity, antiforgery on all state-changing endpoints, login/logout/me
endpoints, a Development-only seed admin from environment variables, and — the
stage's actual deliverable, per the plan's own framing — an end-to-end user
isolation test running against a real, disposable Postgres container. Verified
against a real deployment via `docker compose up` (login → me → authenticated
list → antiforgery rejection → logout → 401) in addition to the automated test.

## Why we built it this way

### The query filter bug the isolation test was built to catch — and did
The first implementation closed over the injected `ICurrentUser` directly:

```csharp
var currentUserIdAccess = Expression.Property(Expression.Constant(currentUser), nameof(ICurrentUser.UserId));
```

This built, and every earlier manual `curl` check that only ever ran as a single
user wouldn't have caught it. The isolation test did: user A created a library
item and then **couldn't see their own item** — only 0 results, for both A and B.
Root cause: EF Core builds and caches its model (compiled query filter included)
once per `DbContextOptions`, then reuses it for every `DbContext` instance.
`Expression.Constant(currentUser)` bakes in the *specific object reference*
resolved at the moment the model was first built — not a live per-request value.
Whichever request happened to trigger that first build "won" permanently, for
every subsequent request, until the process restarted.

The fix is EF Core's documented escape hatch for exactly this: reference `this`
(the `DbContext` instance) inside the filter expression instead of an external
captured object. EF Core specifically rebinds self-references to `this` to the
*actual executing context instance* at query time:

```csharp
public Guid CurrentUserId => currentUser.UserId;   // property ON the context
...
var currentUserIdAccess = Expression.Property(Expression.Constant(this), nameof(CurrentUserId));
```

This is exactly why the plan calls the isolation test "the most important
security test in the project" rather than a nice-to-have — a plausible-looking,
successfully-compiling, manually-spot-checked implementation was actually broken
in a way that (depending on request ordering) could have shown user A's data to
literally everyone, or shown nobody anything. Manual curl testing with one user
logged in at a time could never have surfaced this.

### Setting up Testcontainers now, not deferring further
Stage 2 and Stage 3 both deferred the Testcontainers-backed integration test
project mentioned in plan section 11, verifying instead via real `docker compose`
sessions. Stage 4's isolation test **cannot** be a domain-level unit test — it has
to prove the real HTTP → auth → EF query filter chain works together, which means
a real ASP.NET Core host and a real Postgres. `ApiWebApplicationFactory` (Testcontainers
`PostgreSqlContainer` + `WebApplicationFactory<Program>`, pointed at each other via
`ConfigureWebHost`) is now in place and reusable for any future test needing the
same thing — the deferral ends here, not because a deadline arrived, but because
Stage 4 is the first stage where a real dependency actually requires it.

`Program.cs` needed `public partial class Program;` appended — top-level
statements generate an internal `Program` class by default, invisible to
`WebApplicationFactory<Program>` from another assembly.

### Two users, created by bypassing the API, not by inventing a registration endpoint
There is deliberately no `POST /api/v1/auth/register` (plan: "Извън обхвата:
регистрация през UI... Auth:AllowRegistration = false"). The test creates its two
users directly via `UserManager<ApplicationUser>` resolved from the factory's DI
container — the *setup* bypasses HTTP (there's no HTTP path to use), but the
actual *assertion* (login, create, list, direct lookup) goes through real HTTP
end to end, which is the part that actually needs proving.

### `AddAntiforgery()` needed an explicit `HeaderName`
The default antiforgery configuration only validates a form field
(`__RequestVerificationToken`), which a JSON API never sends — silently a no-op
for every one of our endpoints if left at the default. `options.HeaderName =
"X-XSRF-TOKEN"` turns on header-based validation. Caught this from reading the
docs before wiring it up, not from a failed request — the "verify against docs,
don't guess" habit paying off before shipping something that looked configured
but validated nothing.

### Antiforgery applied per-route, not at the route-group level
`.RequireAuthorization()` is applied once per resource group (works, editions,
library-items, wishlist) since every verb on every one of those resources needs
auth. `AntiforgeryFilter` (an `IEndpointFilter` calling `IAntiforgery.ValidateRequestAsync`)
is instead applied individually to each `MapPost`/`MapPut`/`MapPatch`/`MapDelete`
call — a group-level filter would also run on `MapGet`, and GET requests must stay
token-free.

### Defense in depth: Stage 3's explicit `userId` checks were kept, not removed
Every `LibraryItemService`/`WishlistService` method already filtered by an explicit
`userId` parameter (Stage 3, before the global query filter existed). With the
global filter now in place, those explicit checks are redundant — but they were
deliberately left in rather than cleaned up. Two independent layers enforcing the
same invariant is the right trade for the single most security-critical property
in the app; if the global filter is ever accidentally bypassed (`IgnoreQueryFilters()`,
a future refactor, a raw SQL query), the explicit check is still there.

### `IdentityUserContext<TUser, TKey>`, not `IdentityDbContext<TUser, TRole, TKey>`
Roles are explicitly out of scope for this stage (and not currently planned at
all). `IdentityUserContext` is Identity's role-less base `DbContext` — using it
instead of the role-including variant means no unused `AspNetRoles`/`AspNetUserRoles`
tables get created for a feature that doesn't exist.

### Identity's own tables got explicit snake_case names
`IdentityUserContext.OnModelCreating` hardcodes `ToTable("AspNetUsers")` etc. via
explicit configuration, which the snake_case naming convention (EFCore.NamingConventions)
leaves alone — conventions only apply where no name was set explicitly, and Identity's
base class already set one. Left as PascalCase, this would have been the one
inconsistent corner of an otherwise fully snake_case schema (plan section 7:
"Именуване: `snake_case` таблици и колони"). Overridden explicitly in
`OnModelCreating` to `asp_net_users`/`asp_net_user_claims`/`asp_net_user_logins`/
`asp_net_user_tokens`.

## What's still open

- **DataProtection keys are not persisted.** Noticed in the `docker compose up`
  verification logs: "Storing keys in a directory that may not be persisted
  outside of the container." Auth cookies and antiforgery tokens are encrypted/signed
  with these keys — every container restart currently invalidates every existing
  session. Fine for a single-container Development setup; needs a persisted key
  ring (shared volume or a proper key storage provider) before this matters for
  anything longer-lived. Flagging now so Stage 10 (Docker hardening) doesn't
  rediscover it from a confusing "why did I get logged out" report.
- No lockout/rate-limiting on `POST /auth/login` — `PasswordSignInAsync` was
  called with `lockoutOnFailure: false`. Fine for a single-admin personal app on
  a private network; revisit if this ever needs to be internet-facing.
- `CookieSecurePolicy.SameAsRequest` means the auth cookie is not marked
  `Secure` on plain HTTP (used here for local dev without TLS termination). A
  real deployment behind a reverse proxy terminating TLS (plan section 1: "зад
  един reverse proxy") needs `UseForwardedHeaders` configured too, so the app
  correctly sees the original request as HTTPS — not addressed in this stage.
- Still only the one seed admin account; nothing in this stage adds a way to
  create additional users (deliberately — no registration endpoint exists, and
  none is planned).

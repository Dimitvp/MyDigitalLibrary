## What we built

Plan section 12's Stage 7 scope: `ReadingSession`, progress by format,
ratings, reviews, shelves, notes, quotes. Explicitly out of scope and not
touched — reading goals, statistics. Domain for all of these was already
complete since Stage 1 (with its own unit tests); Stage 7 was Application +
Infrastructure + Api + integration tests, backend-only — no Angular UI this
time (Stage 5 was the dedicated frontend-catchup point; this stage follows
the Stage 3/6 pattern of backend-first, API-verified-by-curl-and-tests).

- **Reading sessions**: `POST /reading-sessions` (captures the library
  item's own `Format`, not a client-supplied one), `POST /{id}/progress`
  (oneOf page/percent/positionMinutes → the matching `ProgressPoint`
  subtype; format mismatches surface as a real 409 from the domain's own
  `ProgressPoint.ValidFor` check), `POST /{id}/finish`, `POST /{id}/abandon`,
  plus `GET` list/detail (not in the plan's list, added since a created
  session needs to be readable).
- **Work rating/review**: `PUT /works/{id}/rating` and `PUT
  /works/{id}/review`, both upsert-by-(UserId, WorkId). `GET /works/{id}`
  now returns the current user's own rating/review inline
  (`WorkDetailDto.MyRating`/`MyReview`) instead of two more GET endpoints.
- **Shelves, notes, quotes**: not in plan section 4's endpoint list at all,
  despite being explicit Stage 7 scope — designed by the same REST
  conventions as every other resource there (plain CRUD + sub-resource item
  operations, `ProblemDetails` errors, 201/204) and added to section 4
  afterward so the plan matches what actually shipped.

## Why we built it this way

### A real, systemic EF Core bug, found by running the code for real

`POST /reading-sessions/{id}/progress` and `POST /shelves/{id}/items` both
came back `500`/`DbUpdateConcurrencyException` on the very first real test
run — not from `dotnet build`, which stayed clean throughout. Traced to the
database logs: EF Core generated an **UPDATE**, not an INSERT, for a
brand-new child row, which naturally affected 0 rows.

Root cause: every entity's `Id` is assigned client-side in `Entity`'s base
constructor (`Guid.NewGuid()`), but no `IEntityTypeConfiguration<T>` in the
project ever told EF Core that explicitly — left at EF's default "value
generated on add" convention for Guid keys. That convention works fine for
every entity added via `db.Set<T>().Add(...)` (an explicit `Add()` sets
`EntityState.Added` unambiguously, no heuristic involved) — which is every
entity in the codebase *except* one: `ProgressEntry`, added not via
`db.Set().Add()` but by appending to `ReadingSession.Progress`, an
already-loaded (`.Include()`), already-tracked collection on an
**already-persisted** `ReadingSession` from a prior request. That's the
first place in this codebase a child gets added to an *existing* tracked
parent rather than a *brand-new* one — and for that "navigation fixup"
discovery path, EF Core has to *guess* Added vs. Unchanged from the key
heuristic, and guesses wrong once the key is already non-default (which,
for this codebase, is always true, since `Entity` sets `Id` before EF ever
sees the object).

Fixed with `.Property(x => x.Id).ValueGeneratedNever()` on `ProgressEntry`
and `ShelfItem` (both newly exercised this stage), and proactively on
`WorkAuthor` and `PriceHistoryEntry` too — the identical latent bug, not yet
triggered only because nothing yet adds an author to an *existing* Work or
a price observation to an *existing* `BookstoreListing` (Stage 8's
availability refresh will do exactly that). Verified metadata-only before
and after with `dotnet ef migrations add` (empty migration both times — no
DDL change, confirmed rather than assumed), then verified the actual fix
against a running deployment: recording progress and adding a shelf item
both went from `500` to succeeding, checked by hand before rolling the same
fix out to the two not-yet-exercised cases.

### Shelves/notes/quotes: designed by convention, then written back into the plan

Section 4 lists contracts for every other resource in the app but is
silent on these three, even though Stage 7's own one-line scope names them
explicitly ("рафтове, бележки, цитати"). Rather than stop and wait, or
silently invent something inconsistent with the rest of the API, designed
them using the exact same shape every other resource in section 4 already
uses — then added the result back into section 4 as its own `docs:` commit
(`5db42d7`) so a future session finds them documented rather than
rediscovering the same gap.

### Rating/review folded into `WorkDetailDto`, not two more GET endpoints

A `WorkRating`/`Review` is a single per-user value tied to a work a UI would
almost always want alongside the rest of a work's detail view — adding
`GET /works/{id}/rating` and `GET /works/{id}/review` as parallel
micro-endpoints would have meant three round-trips for one screen. Folded
both into the existing `GET /works/{id}` response instead.

### Review upsert: implemented the open question's simpler branch, not a guessed final answer

Plan section 14 Q4 ("versioned review history, or does the latest
overwrite?") is explicitly listed as unresolved for the project owner.
`PUT /works/{id}/review` implements last-write-wins (no history) — the
`PUT` verb's natural semantics, and the simpler of the two options — as a
working default, not as a silent decision on the owner's behalf. Flagged in
both the endpoint's own doc comment and the plan itself (still marked open
in section 14).

## What's still open

- No Angular UI for any of Stage 7's features (reading sessions, ratings,
  reviews, shelves, notes, quotes) — deliberately deferred; Stage 5 was the
  dedicated frontend-catchup stage and no later stage in the plan explicitly
  asks for a repeat until one does.
- Review versioning (plan section 14 Q4) is still an open question for the
  project owner — current behavior is last-write-wins.
- `GET /reading-sessions` takes `libraryItemId` as a required query filter
  with no pagination — fine at personal scale (a handful of sessions per
  book), would need revisiting if that ever stops being true.
- The `ValueGeneratedNever()` fix was applied to every currently-known
  "child added to a parent's collection via an aggregate method" case found
  by inspection (`WorkAuthor`, `PriceHistoryEntry` included pre-emptively) —
  a future stage introducing a new such pattern should apply the same fix
  proactively rather than wait to rediscover the bug.

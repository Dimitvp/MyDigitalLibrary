# Автоматично теглене на production backup към локалната машина — пълен наръчник

**Date:** 2026-09-17
**Context:** След преместването на каноничната база на production сървъра
(`biblioteka.svara.bg`, вижте `2026-09-17-1700-local-to-production-data-migration.md`),
собственикът попита какво се случва с backup механизма при това ново
разположение. Отговорът разкри, че production вече сам си пази backup-и, но
те всички живеят физически на едно и също Hetzner устройство — включително
седмичния VM snapshot на самия Hetzner. Решено бе да се добави истинско
off-site копие: локалната машина сама си тегли най-новия production backup
на график.
**Status:** Завършено и работещо. Scheduled Task е регистриран и потвърден
`Ready`, скриптът е тестван ръчно и успешно изтегли реален файл.
**Commits:** `6b187fb` — `feat: automate off-site backup pull from production`

## 1. Защо изобщо трябваше това

Преди тази промяна имаше **три** копия на данните, но всичките зависеха от
един и същ доставчик:

1. Живата база в `biblioteka-pgdata` Docker volume-а на production сървъра.
2. `db-backup` sidecar контейнерът на production, който прави `pg_dump` на
   всеки ~5 мин. след промяна (или седмично) в `/opt/biblioteka/db-backup/`
   — **на същия диск** като точка 1.
3. Hetzner-ският собствен седмичен snapshot на целия сървър — **на същия
   Hetzner акаунт** като точки 1 и 2.

Ако Hetzner акаунтът/сървърът стане недостъпен (спряна сметка, хардуерен
проблем, компрометиран root достъп), и трите копия изчезват едновременно.
Липсваше копие, което физически да живее другаде. Оттам идва новият, четвърти
механизъм.

## 2. Как работи (общ поглед)

```
production (46.62.253.87)                    локална машина (тази, на която пишеш)
┌─────────────────────────┐                  ┌──────────────────────────────┐
│ db-backup sidecar        │                  │ Windows Task Scheduler        │
│ прави pg_dump на всеки    │                  │ "MyDigitalLibrary-            │
│ ~5 мин. промяна           │                  │  PullProductionBackup"        │
│      ↓                    │                  │ (всеки ден, ~13:33)           │
│ /opt/biblioteka/db-backup/│  ←── SSH/scp ──  │      ↓                        │
│ mydigitallibrary_*.dump   │                  │ db-backup/pull-from-          │
└─────────────────────────┘                  │ production.ps1                │
                                              │      ↓                        │
                                              │ D:\...\MyDigitalLibrary\      │
                                              │ db-backup\                    │
                                              │ mydigitallibrary_*.dump       │
                                              └──────────────────────────────┘
```

Няма нищо инсталирано на сървъра за тази конкретна стъпка — production просто
си прави backup-ите, както винаги е правил. Цялата нова логика живее
**локално**: скрипт, който се login-ва по SSH, пита за най-новия файл, и ако
локално го няма, го тегли със `scp`.

## 3. Файлове и къде точно живеят нещата

| Какво | Път | Забележка |
|---|---|---|
| Скриптът, който тегли | `db-backup/pull-from-production.ps1` (в git repo) | Единственият нов файл, който се проследява от git |
| Локална папка за dump-ове | `db-backup/` (в repo, но самите `.dump` файлове са в `.gitignore`) | Същата папка, която `docker/db-init/10-restore-if-exists.sh` вече чете за локален restore |
| Лог от всяко изпълнение | `db-backup/pull-from-production.log` (gitignored) | Append-only, ред на изпълнение с UTC timestamp |
| Production backup папка | `/opt/biblioteka/db-backup/` на сървъра | Пълни се от `biblioteka-db-backup` контейнера (виж `docker-compose.prod.yml`) |
| Windows Scheduled Task | `MyDigitalLibrary-PullProductionBackup` | Виж `Get-ScheduledTask` по-долу — конфигурацията е **локална за тази машина**, не е в git |

Имената на файловете винаги са `mydigitallibrary_<UTC timestamp>.dump`, напр.
`mydigitallibrary_20260917T095509Z.dump` — сортират се хронологично по име,
затова скриптът може просто да вземе последния по азбучен ред без да чете
съдържание.

## 4. Как комуникира с сървъра

- **Протокол:** чист SSH/scp, никакъв допълнителен API или порт. Скриптът
  изпълнява `ssh root@46.62.253.87 "ls ... | sort | tail -n 1"` за да разбере
  кой е най-новият файл, после `scp` за самото сваляне.
- **Автентикация:** същият SSH ключ, който вече се ползва за деплой
  (`~/.ssh/id_ed25519` по подразбиране на тази машина — няма отделен запис в
  `~/.ssh/config` за host `46.62.253.87`, така че се ползва default ключа).
  **Ако този ключ някога се смени/ротира, скриптът ще спре да работи** без
  никаква промяна в самия `.ps1` файл — просто SSH ще откаже достъп.
- **Права:** скриптът чете от production, никога не пише там — чисто
  read-only спрямо сървъра. Няма риск да развали нещо на production, дори
  при бъг в скрипта.
- **Мрежа:** сървърът трябва да е достъпен на познатия адрес
  (`46.62.253.87`, root SSH) — ако IP-то на сървъра се смени, трябва да се
  редактира `$Server` в скрипта.

## 5. Как да го редактираш

Отвори `db-backup/pull-from-production.ps1` — всичко е в параметри най-горе:

```powershell
$Server = 'root@46.62.253.87'          # смени ако сървърът се мигрира
$RemoteDir = '/opt/biblioteka/db-backup'  # смени ако пътят на сървъра се промени
$LocalDir = $PSScriptRoot               # винаги = папката, в която е самия скрипт
```

Няма нужда от нищо друго за промяна на поведението — логиката (намери
най-новия remote файл → провери дали го имаш локално → изтегли ако не) е
достатъчно проста да се чете директно в скрипта (58 реда, вижте самия файл).

След промяна: **не е нужно да пререгистрираш Scheduled Task-а** — той просто
изпълнява файла по път всеки ден, така че редакция на съдържанието му се
взима автоматично при следващото изпълнение.

## 6. Как да проверяваш/управляваш Scheduled Task-а

```powershell
# Статус, следващо/последно изпълнение
Get-ScheduledTask -TaskName "MyDigitalLibrary-PullProductionBackup" | Get-ScheduledTaskInfo

# Ръчно изпълнение веднага (полезно за тест, не чака графика)
Start-ScheduledTask -TaskName "MyDigitalLibrary-PullProductionBackup"

# Пълни детайли (тригер, действие, настройки)
Get-ScheduledTask -TaskName "MyDigitalLibrary-PullProductionBackup" | Format-List *
```

**Текущ график:** ежедневно, ~13:33 (часът се определи автоматично от
момента на регистрация — не е нарочно избран 9:00, както можеше да се очаква
от първоначалния `-At 9:00AM`, защото после `$trigger.StartBoundary` беше
презаписан с текущото време). Ако предпочиташ друг час:

```powershell
$task = Get-ScheduledTask -TaskName "MyDigitalLibrary-PullProductionBackup"
$task.Triggers[0].StartBoundary = "2026-09-18T09:00:00"
Set-ScheduledTask -InputObject $task
```

**Важно ограничение:** Task-ът е настроен да работи само докато потребителят
е logged in (иначе няма достъп до SSH ключа/agent-а). Ако машината е
изключена или той не е логнат в 13:33, `-StartWhenAvailable` кара Windows да
го пусне при следващото включване/логин вместо да го пропусне напълно.

## 7. Как да проверяваш дали работи

1. **Логът е първото място за гледане:**
   ```powershell
   Get-Content "D:\01. Work\MyDigitalLibrary\db-backup\pull-from-production.log" -Tail 20
   ```
   Всеки ред е `<UTC timestamp> <съобщение>` — или "Already have the newest
   snapshot" (нормално, нищо ново от вчера), или "Pulled X successfully",
   или "ERROR: ...".
2. **Папката трябва да расте бавно с времето:**
   ```powershell
   Get-ChildItem "D:\01. Work\MyDigitalLibrary\db-backup\*.dump" | Sort-Object LastWriteTime
   ```
   Ако най-новият файл тук е много по-стар от няколко дни, нещо се е
   счупило — виж троубълшутинг по-долу.
3. **`LastTaskResult` от `Get-ScheduledTaskInfo`:** `0` = успешно последно
   изпълнение. Друга стойност (напр. `267011` = "все още не е изпълняван")
   не е непременно грешка — виж и лога, той е по-точен.

## 8. Троубълшутинг — ако нещо се обърка

| Симптом | Вероятна причина | Какво да провериш |
|---|---|---|
| Логът показва `ERROR: ... Permission denied` | SSH ключ сменен/изтрит, или production е спрял да го приема | `ssh root@46.62.253.87 echo ok` ръчно от тази машина |
| Логът показва `No backup files found on production` | `db-backup` sidecar-ът на production не работи | `ssh root@46.62.253.87 'docker ps --filter name=biblioteka-db-backup'` на сървъра — трябва да е `Up`, не `Restarting` |
| Скриптът не се е изпълнявал изобщо (`NextRunTime` в миналото, `NumberOfMissedRuns` > 0) | Машината е била изключена/не си логнат по време на графика | Пусни ръчно с `Start-ScheduledTask`, провери дали `-StartWhenAvailable` е активно (`Get-ScheduledTask ... \| Select Settings`) |
| `scp exited with code X` в лога | Мрежов проблем, сървърът недостъпен, или дискова квота свършила локално | Провери свободно място на `D:`, провери `ping 46.62.253.87` |
| Файлът се тегли всеки път наново (дублира се) | Малко вероятно — логиката е by-filename, но ако timestamp форматът на production някога се смени, сравнението ще се счупи | Провери дали имената на файловете в `/opt/biblioteka/db-backup/` все още следват `mydigitallibrary_<timestamp>.dump` |
| Искаш да пренесеш проекта на нова машина и теглянето спре | Task Scheduler конфигурацията е **локална**, не е в git | Пусни ръчно командите от `db-backup/README.md` (`Register-ScheduledTask` блока) на новата машина |

## 9. Връзка с останалите механизми (за пълна картина)

- **Production→production backup** (`db-backup` sidecar в
  `docker-compose.prod.yml`, скрипт `docker/db-backup/backup.sh`): прави
  `pg_dump` вътре на production при промяна в данните. Независим от този
  механизъм — работи си както преди, тук само добавяме теглене на резултата.
- **Локален restore при празен volume**
  (`docker/db-init/10-restore-if-exists.sh`): чете **същата** `db-backup/`
  папка локално и възстановява от най-новия `.dump` при старт на празна база.
  Изтеглен production snapshot автоматично участва в това — без допълнителна
  логика, просто защото пада в същата папка и печели по timestamp сортиране,
  ако е по-нов от локалните backup-и.
- **Retention/prune политика** (описана в `db-backup/README.md`): пази поне
  10 файла, трие само по-стари от ~6 месеца измежду излишните — важи еднакво
  за локално-генерирани и изтеглени-от-production файлове, защото и двата
  вид просто са `.dump` файлове в същата папка.
- **Hetzner седмичен VM snapshot**: изцяло отделен, управляван от Hetzner
  Cloud конзолата, не от този repo. Покрива целия диск (вкл. кода, не само
  базата), но остава "вътре" в Hetzner — точно затова трябваше този нов,
  истински off-site механизъм.

## What we built

Plan section 12's Stage 9 scope, all seven sub-features:

- **Loans** — `POST /library-items/{id}/loans`, `POST /loans/{id}/return`.
  Lending an item flips its `OwnershipStatus` to `LentOut`; returning it
  flips it back only if the status is still `LentOut` (a manually-changed
  status in between is left alone). Rejects a second concurrent loan on the
  same item.
- **Reading goals** — `GET/PUT /reading-goals/{year}`, upserted by
  `(UserId, Year)`. Progress (books finished, pages read) is computed from
  finished reading sessions and edition page counts within the calendar
  year, using a `DateOnly` range comparison rather than `.Value.Year`
  inside `.Select()` to stay safely within what EF can translate to SQL.
- **Export** — `GET /export?format=json|csv`. JSON is a full denormalized
  archive (library items, wishlist, shelves, notes, quotes, loans, reading
  sessions, reading goals); CSV covers library items only, by a hand-rolled
  RFC 4180 writer (a flat CSV can't represent the nested archive).
- **Statistics** — `GET /statistics?year=`. Totals by format/status, books
  finished and pages read this year, currently-reading count, average
  rating, top 5 authors by owned-item count.
- **Duplicate detection** — `GET /duplicates`. Exact-match only (no fuzzy
  matching — `pg_trgm` was out of scope and unverified): Works matched
  catalog-wide by trimmed/case-folded title; LibraryItems matched per-user
  by `(EditionId, Format)` — owning the same book as physical + ebook is
  correctly *not* flagged (plan 3.1).
- **CSV import** — `POST /import/csv` (multipart), auto-detects Goodreads
  vs. Calibre export shape, parses with CsvHelper, imports synchronously
  (deliberate YAGNI — no background queue) with per-row `try`/`catch` so
  one bad row doesn't abort the batch. `GET /import/jobs/{id}` for the
  resulting job record.
- **Full-text search** — `GET /search?q=...`. PostgreSQL generated
  `tsvector` column + GIN index over `Work.Title`/`OriginalTitle`/
  `Description`, unioned with a separate author-name tsvector match. Uses
  the `simple` text search configuration throughout.

## Why we built it this way

### Real research before writing code, three times over

Every sub-feature that touched an external format or a Postgres-specific
mechanism was verified against reality before being designed, not guessed:

- **CSV formats**: Goodreads' and Calibre's real export column sets were
  looked up (WebSearch), not invented — including Goodreads' `="1234567890"`
  Excel-formula ISBN-wrapping quirk, which a correct RFC 4180 parser
  (CsvHelper) chokes on if the test fixtures don't escape it exactly right.
  Caught for real by running the tests, not by inspection: three fixtures
  had unescaped `="..."` sequences and came back with `null` fields until
  fixed.
- **No Bulgarian stemmer**: the plan itself hedges that PostgreSQL likely
  has no built-in Bulgarian dictionary and says to verify before designing.
  Spun up a real, disposable `postgres:17-alpine` container, ran `\dFd`
  (29 snowball stemmers, no Bulgarian), and confirmed the `simple`
  configuration correctly tokenizes and matches real Cyrillic text before
  writing `WorkConfiguration`'s shadow property.
- **The real Npgsql API surface**: `IsGeneratedTsVectorColumn`,
  `HasMethod("GIN")`, `PlainToTsQuery`, `ToTsVector`, `.Matches(...)` were
  confirmed against the installed package's own XML docs (grepped from the
  NuGet cache), not assumed from memory.

### A genuine layering question, resolved by principle rather than convenience

`SearchService.cs` (Application layer) needs `NpgsqlTsVector` and the
Npgsql-specific EF LINQ extensions (`EF.Functions.ToTsVector`,
`PlainToTsQuery`, `.Matches`) to build its query — these live in
`Npgsql.EntityFrameworkCore.PostgreSQL`, a package every other project
convention treats as Infrastructure-only (see `Directory.Packages.props`'s
own `<!-- Infrastructure -->` grouping). This looked at first like a
boundary violation.

Resolved by distinguishing *project references* (forbidden — Application
must never reference Infrastructure) from *NuGet package references*
(fine, when the package is a technology the layer has already committed
to). Application already depends on `Microsoft.EntityFrameworkCore`
directly — this plan never asked for database-provider abstraction, it
asked for PostgreSQL specifically (plan section 1: "PostgreSQL 17"). Adding
`Npgsql.EntityFrameworkCore.PostgreSQL` as a second, more specific EF
package reference in Application is consistent with that existing
commitment, not a new one. Moved the package under a shared comment
grouping in `Directory.Packages.props` documenting this reasoning inline,
so a future session doesn't have to re-derive it.

### Two real bugs, found only by running the tests

`IClassFixture<ApiWebApplicationFactory>` shares one Testcontainers
Postgres across every test *method* in a class (not just the class itself).
This bit two features in this stage:

- **Export tests**: two test methods both hardcoded the same ISBN via a
  shared helper — the second hit the real unique-ISBN index and got `409`
  instead of `201`. Fixed by dropping the hardcoded ISBN (not needed for
  what those tests actually assert).
- **Statistics/ReadingGoals tests**: `ReadFromJsonAsync<JsonElement>()`
  was called twice on the same already-consumed `HttpContent` stream,
  silently returning nothing the second time. Fixed by reading once into a
  local variable.

Neither would have been caught by static review — both only showed up
because the tests were actually run against a real database, per the
project's standing discipline.

### Full-text search verified against a real Docker deployment, in Cyrillic

Beyond `dotnet test`, brought up the full `docker compose` stack for real
(had to reconstruct a local `.env` from `.env.example` — gitignored, never
committed), applied the `AddWorkSearchVector` migration for real, created a
library item with a genuinely Cyrillic title/author ("Дюна" / "Франк
Хърбърт") over HTTP, and searched for it. First attempt came back empty —
turned out to be this environment's shell mangling literal Cyrillic passed
as inline `curl` arguments (confirmed by checking the raw bytes: writing
the same text to a file and having `curl --data-urlencode "q@file"` read it
from disk instead worked immediately, matching both by title and by
author). Not a product bug — a reminder that any verification step passing
non-ASCII text through this shell needs to go via a file, not an inline
argument.

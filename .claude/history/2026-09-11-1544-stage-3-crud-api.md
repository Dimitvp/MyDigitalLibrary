## What we built

The full Stage 3 surface from `docs/PLAN.md` sections 4/4.1: REST endpoints for
`works`, `editions`, `library-items`, and `wishlist`, backed by a new Application
layer (ports, DTOs, per-resource services) and an `IApplicationDbContext` adapter in
Infrastructure. ProblemDetails (RFC 9457) with an `errorCode` extension for every
error path, pagination, and the composite create flow from section 4.1 (create a
Work + Edition + LibraryItem in one request/transaction, since there is no
`POST /works` or `POST /editions`). Every endpoint was exercised against a real
Postgres container via `docker compose up` + `curl`, not just compiled.

## Why we built it this way

### Application layer: `IApplicationDbContext`, not a repository per aggregate
The plan's layering (`Domain ← Application ← Infrastructure ← Api`) means Application
can't reference Infrastructure's `MyDigitalLibraryDbContext` directly. Rather than
hand-writing a repository interface per aggregate (`IWorkRepository`,
`ILibraryItemRepository`, ...) — a lot of boilerplate for what's fundamentally CRUD —
Application defines `IApplicationDbContext` exposing the `DbSet<T>`s it needs plus
`SaveChangesAsync`, and Infrastructure's real DbContext just declares
`: IApplicationDbContext` (every member already matched, so no new code was needed
there). This is the same pattern as the "Clean Architecture" template's
`IApplicationDbContext` — a well-precedented trade-off, not an invented one. It does
mean Application has a `Microsoft.EntityFrameworkCore` package reference (for
`DbSet<T>`), which Domain is still forbidden from having.

### Services, not one class per use case
The plan says "use cases... извикай use case класа директно през DI" without
mandating one class per action. Given four resources with several operations each,
one **service class per resource** (`WorkService`, `EditionService`,
`LibraryItemService`, `WishlistService`) with a method per operation was the
pragmatic reading — still "call it directly, no MediatR," just less boilerplate than
~17 single-method classes for what's straightforward CRUD.

### `ICurrentUser` introduced now, trivially implemented
Stage 4 (auth) doesn't exist yet, but `LibraryItem`/`WishlistEntry` already require a
`UserId`. Rather than hardcoding the seeded dev user's Guid inside every service
method, `ICurrentUser` (Application port) + `FixedCurrentUser` (Infrastructure,
returns `DevelopmentSeeder.DevUserId`) was added now. Stage 4 swaps the
implementation for one backed by `HttpContext.User`; no Application code changes.

### EF Core can't translate `.Where()` applied after a constructor-projection `.Select()`
Every `GetAsync`/detail query originally did `Project(db).Where(x => x.Id == id)` —
project to a DTO-shaped record first, then filter. This built and looked correct but
threw `InvalidOperationException: ... could not be translated` at **runtime**, caught
only by actually hitting the endpoint through Docker (`GET /works/{id}`,
`GET /editions/{id}`, `GET /works/{id}/editions` all 500'd). The fix: filter on the
raw entity `IQueryable<T>` first, project second — `Project(db.Editions.Where(...))`
instead of `Project(db.Editions).Where(...)`. `EditionService.Project` and
`WorkService`'s private `Project` now both take an already-filtered
`IQueryable<TEntity>` rather than building the query internally, specifically so this
ordering mistake can't happen again by construction.

### Value-converted property members can't be selected inside a query, only the property itself
`Edition.Isbn13` (`Isbn?`, via `HasConversion`) and `Edition.Duration`
(`AudioDuration?`, same) can be selected as a whole inside `.Select()`, but accessing
`.Value`/`.TotalMinutes` on them *inside* the same expression can't translate to SQL —
EF has no way to push arbitrary CLR code that runs *after* the converter into the
database. `EditionRow` (internal) carries the raw converted properties; `.ToDto()`
unwraps them in a second, in-memory step. This is the reason a "Row → DTO" split
exists for Editions/Works but not for LibraryItems/WishlistEntries — `Acquisition`,
`Money`, and `PhysicalLocation` are owned types (real relational structure EF
understands member-by-member), not `HasConversion` scalars, so selecting
`li.Acquisition.Price.Amount` directly inside a query works fine.

### `WishlistEntryDto` mapping is done in-memory, not via `Select()`
`WishlistEntryMapper.ToDto` is a plain static method, not an expression tree — calling
it inside `.Select(w => WishlistEntryMapper.ToDto(w))` against `IQueryable<WishlistEntry>`
would fail exactly like the two issues above (EF can't see inside an opaque method
call). `ListAsync` materializes entities via `ToListAsync()` first, then maps with
LINQ-to-Objects. Caught this one before it shipped, from the pattern of the other two
failures, not from hitting it live.

### `LibraryItem.UpdateAcquisition` — a real domain gap, not scope creep
`PUT /library-items/{id}` needed to edit acquisition details (you mis-entered the
price, the date, whatever), but `LibraryItem` had `SetLocation`/`ChangeStatus`/
`SetPersonalNote` and no way to change `Acquisition` after construction. Added
`UpdateAcquisition(Acquisition)` — one line, same pattern as the existing setters —
plus a domain test, before touching Application code that depends on it.

### `docs/PLAN.md` section 4.1 was drafted by this session, then substantially rewritten externally
The user's instruction referenced a "section 4.1" that didn't exist on disk yet (verified
before acting). A first version was drafted in this session (`da30bf5`), matching the
described `oneOf` shape. It was then rewritten externally with a cleaner design — one
endpoint per resource (not per Work/Edition), authors referenced by plain name strings
rather than pre-existing ids, `edition.duplicate` as the standardized dedup error code,
and an explicit completion criterion for Stage 3 ("add a book from scratch, find it,
edit it, delete it, entirely through the API"). The implementation in this stage matches
that final, externally-revised version, not the first draft.

### `shelfId` filter on `GET /library-items` reaches into Shelf, a Stage 7 concept
The endpoint's query contract (`?shelfId=`) was fixed back in Stage 1/plan section 4.
Shelf/ShelfItem already exist as entities (Stage 1) even though shelf *management* is
Stage 7 scope. Rather than silently ignore a documented query parameter, `ListAsync`
filters via `db.Shelves.Any(...)` — reusing what already exists, not building shelf
management early.

### UTF-8 false alarm
An early composite-create test with Cyrillic text in the request body stored as
`"????: ???????"` in Postgres — looked like a real encoding bug in the API. It wasn't:
a follow-up test writing the same payload to a file first (`--data-binary @file`)
round-tripped correctly (`Тест Кирилица` came back intact via `psql`). The corruption
was specific to typing Cyrillic literals inline into a Bash heredoc/command string on
this Windows machine, not the request/response/database pipeline. Worth remembering
before assuming an encoding bug is in the application next time this comes up.

## What's still open

- No Application-layer unit tests yet (plan section 11 lists NSubstitute for mocked
  ports) — this stage's verification was end-to-end against real Postgres instead.
  Worth adding once the shape of the services stabilizes further.
- Author/series matching for composite create is exact-string, case-sensitive
  (`FullName == trimmed`). Will produce duplicate Authors for "Frank Herbert" vs
  "frank herbert" vs "Frank  Herbert" (double space). Acceptable for manual v1 entry;
  revisit if this becomes a real annoyance before Stage 6 (import) needs the same
  matching logic at higher volume.
- `DeriveSortName`'s last-token heuristic doesn't handle non-Western name orders or
  multi-word surnames correctly. Flagged as a known simplification in the code comment,
  not silently assumed correct.
- Query filtering by `q=` on `GET /library-items` does a case-sensitive `Contains` via a
  join to the edition's Work title — no case-insensitive or fuzzy matching. Full-text
  search is explicitly Stage 9 scope.
- `PhysicalLocation` EF warning and `libgssapi_krb5.so.2` message from Stage 2 are still
  present and still harmless/expected (see Stage 2's history entry).
